# Architecture

## Decisions

- React + TypeScript + Vite for the interactive client; Fastify for a loopback-only local service.
- Markdown body + YAML frontmatter, one record per file. The API exposes parsed records with a SHA-256 revision derived from exact file bytes.
- Zod validates the initial entity contract. Future user-defined schemas should use JSON Schema and Ajv, with explicit migrations.
- TanStack Query owns server state. React component state owns temporary UI choices. A single command API owns mutations.
- Motion provides presentation transitions. HTML/CSS and SVG are the baseline rendering technologies.
- No mandatory database. A future SQLite/FTS5 index is derived and rebuildable, never authoritative.
- Git is version control, not real-time collaboration. The data folder may be a separate repository.
- Avoid desktop packaging, plugin runtimes, canvas engines and 3D libraries until their respective vertical slices are implemented.

## Data flow

File -> parse -> validate -> query -> projection (board/table/gallery/slides).
Inspector -> validated command + expected revision -> atomic write -> query invalidation -> all projections.

The current client polls the local API. A future file watcher plus server events can reduce polling. A stale revision returns HTTP 409. Invalid external files produce visible errors instead of being silently discarded. Atomic replacement prevents partial writes but cannot guarantee transaction isolation against non-cooperating external processes; the server serializes its own writes. Multi-record transactions and recovery journals are later work.

## Project format

`records/<id>.md`: YAML frontmatter with id, type, title, status, priority, tags, accent and relationships, followed by a Markdown body. Stable identifiers are generated by the server. Optional image/media support is later work; persisted view definitions are implemented as described below.

## Security boundary

Single local user. Server binds to loopback, validates Host and Origin, accepts JSON writes, and never executes record content. Record identifiers cannot contain path separators; symbolic-link record files are rejected. Remote access requires a separate authentication, authorization and deployment design. Do not expose this server through a reverse proxy.

## Multi-project boundary

The local registry is a YAML file containing explicitly configured absolute paths; the browser only sends validated project IDs. Each project has its own RecordStore, API URL namespace, and query cache namespace. Standalone projects keep records/; repository-mode projects use .prism/records/. A registry is machine-local; project records should remain Git-tracked. The browser cannot specify arbitrary root directories.

The initial repository reader is a bounded, read-only inventory of recognized source, documentation and manifest files in conventional directories. It rejects traversal and symlinks and never invokes compilers or project scripts. It is not a semantic parser or a sandbox for hostile local processes. Future adapters should emit normalized derived records with provenance (source, revision, timestamp, extraction method), kept separate from authored content. Runtime tools must be explicitly approved and disabled by default.

Audit findings are computed from canonical records, not stored as independent facts. Current checks cover missing descriptions and unresolved/self references; they do not imply implementation or verification coverage.

## Saved views and knowledge

View definitions are separate, versioned YAML files under the same project data root's views/ directory (repository mode: .prism/views/). They contain only configuration, not record copies. Each file has a stable ID and revision derived from bytes. Create/update/delete use a per-project serialized store, atomic replacement for writes, and optimistic conflict checks. Saved view queries use a shared pure selection function. Links and backlinks are computed from the canonical record list; they are not duplicated on disk. Relationships accept legacy string IDs (generic) and explicit {kind, target} objects. The shared relationship module derives labeled inverse edges and checks known endpoint constraints; Audit reports invalid endpoints and unresolved links. No inferred semantic migration or duplicate inverse storage. Wiki uses record bodies and the repository browser renders original Markdown, with raw HTML, external images and link navigation disabled. Neither is AI-generated documentation.

## Self-management workspace
The tracked .prism/projects.yaml is a portable registry with Prism's repository root as its first entry. Its records and saved views are real product knowledge, not frozen fixtures. A machine-local registry takes precedence. The read-only repository inventory supports src/, server/, shared/ and conventional documentation and test folders. Because Prism contains the examples, source browsing can include their tracked code, while their hidden data stores remain excluded and independently scoped. See docs/development-workflow.md for ownership and change conventions.

## Purpose-driven interface
The shared navigation module maps project profiles to purpose destinations with a default record filter and allowed view modes. This is a built-in configuration, not yet a user-editable navigation schema. Overview projections are derived directly from canonical records: active milestones, open tasks explicitly tagged blocker, task status counts and ordered milestone titles. Ready is an authored status, not proof of verification. Raw collections remain in Data library and saved view definitions remain independent. The same inspector supports expanded editing without remounting its draft state. No additional project data or dependencies are required.

## Git delivery evidence
Git is authoritative for commit history. The read-only adapter requires independent Git metadata and verifies the exact configured worktree root, captures HEAD, then reads at most 101 commits (100 displayed, one for truncation detection) with fixed argv, timeout and bounded output. It does not run scripts, change refs, request diffs or fetch remotes. Git must be installed and the repository trusted locally. A shallow or truncated history is explicitly partial. The optional implementationCommits metadata stores reviewed exact historical hashes, preserved by ordinary editor saves; new changes use Prism-Record trailers. Derived attribution never sets authored status or establishes CI acceptance. The browser cannot supply a Git command or arbitrary root.

## Local verification evidence
Explicit CLI execution in the trusted Prism checkout runs fixed npm commands and captures exit results plus Git revision/cleanliness at start and end. No browser route launches it. Latest report is an ignored local cache file, not an authenticated attestation. Repository-scoped reader validates size, regular-file paths and versioned schema. Quality compares reported revision to observed Git HEAD and reports historical or diagnostic evidence separately. Later uncommitted edits and transient changes during the run are not excluded by start/end observations; manual acceptance and current git status are still required.

Navigation uses a single immutable destination/mode/filter/saved-view snapshot. A canonical relative mode order defines the toolbar independently of the destination default, and the knowledge shell is loaded with the app; only Markdown rendering is lazy within the article. Knowledge focus is scoped to destination and saved view, not shared between unrelated Wiki/Relationships categories. This avoids coupling common navigation to a whole-view asynchronous boundary; browser acceptance is still required.

Personal mode preferences are versioned browser-local storage entries keyed by configured project ID and destination ID, with session-memory fallback for inaccessible storage. Read and validate the preferred mode before navigating; only explicit mode changes in an ordinary destination are remembered. Saved views retain their authored configuration. Preferences neither enter Git nor modify records. Filters and active destination are not persisted by this slice; browser origin/profile and registry ID define the preference scope.

## Recoverable editing
The editor holds a versioned base revision, editable baseline and draft. Browser-local recovery stores that envelope by registry project ID and record ID; it permits incomplete title/tag input while the canonical save uses strict editable validation. Writes compare the last observed recovery token and report competing storage changes; this is not an atomic cross-tab lock. Closing dirty edits requires a confirmed recovery copy; explicit discard and JSON export are available. Reopening restores the draft. When a disk revision changes, a field-level three-way comparison preserves disk-only edits and requires explicit choices for overlapping fields. Applying a resolution rebases the draft only; a later API save still uses the current expected revision. A 409 refreshes the record without clearing the draft. Browser storage is origin/profile-specific and quota-limited, not a backup; an open editor retains its last record snapshot when its canonical file disappears or becomes invalid, blocks save and permits recovery/export. Orphan drafts after reopening require restoring the file first. Filesystem recovery, orphan-draft management, text-level merging, undo/redo and autosave remain future work.

## Addressable workspace
Routes use stable project IDs and category, saved view or record IDs in URL fragments: #/projects/prism/work, #/projects/prism/saved/10-acceptance, #/projects/prism/records/draft-recovery. Fragment routing works in both the Vite preview and static Fastify build without a catch-all server route. Browser history is authoritative for visits; versioned history entries validate collection context, reader focus, presentation index and bounded scroll. Default selection remains independent of canonical tab ordering. Back/Forward restore visited context (scroll is best effort for asynchronous content); breadcrumb links navigate the hierarchy. Record identity is type-independent; parent category derives from current type/profile. Native links allow direct new-tab navigation. Guard dirty/pending editor or record creation across managed in-app history; document unload retains the existing browser warning. Record pages are read-only by default and explicit editing reuses the same draft and revision system. Linked tests and open acceptance-tagged Test records are derived from canonical records. No independent task copy or automated acceptance. Full browser validation, repository-file internal navigation and structured acceptance outcomes remain future work.

## Acceptance execution and motion
Acceptance-tagged Test Markdown remains the single authored definition. Structured cases use a level-two group heading `## A. Group title` and one bullet `- [ ] A01 — **Case title** — Action. Expected: Result.`; setup may precede cases inside each group. Unsupported or malformed definitions are not silently executed. Existing checked boxes do not establish past evidence. For connected independent Git repositories, AcceptanceStore snapshots the definition, record revision and observed Git HEAD at explicit run creation. Local files in `.prism/acceptance.local` (ignored by `*.local`) use strict bounded JSON schemas, validated file IDs, atomic temp-file replacement, process-local serialization and run revision checks. Update only open runs at the same observed HEAD and definition revision; historical and finalized runs are retained. Result notes required for failed/blocked cases; manual accept requires all cases passed and explicit decision notes. Store matching local verification report if available, without assuming current working-tree cleanliness. Review JSON export supports deliberate evidence sharing/backups. No automatic task status, PR merge, remote writes or distributed locking. Standalone/other Test records remain readable.
The main content animates on actual route visits with a 160ms small directional shift and fade, not on filter/query updates. Back reverses direction; case changes and progress have short matching transitions; prefers-reduced-motion bypasses motion. Navigation shell remains mounted. Unsaved review observations share the editor's navigation guard and require explicit save or discard; unlike record drafts, unsaved case text is not crash-recoverable. Saved results and local case-position preference persist on return.

## Editor sessions and local browser verification
The editor retains an immutable entry recovery checkpoint, resets it after successful canonical save or explicit draft discard, and compares actual draft/base fields rather than timestamps. Cancel restores that checkpoint via the existing recovery token check; it never overwrites competing-tab data. Guarded navigation displays a dismissible floating status toast without shifting content. Review Save & next advances only after an acknowledged write. Copy review summary escapes authored content and formats saved run outcomes and matching verification, without network publication.
The browser regression runner uses a temporary independent Git repository and standalone project with an explicit registry override, a production build, non-reused loopback server and a test fixture identity assertion before writes. Results/traces/screenshots are ignored local evidence. It compares application Git HEAD/cleanliness before and after the suite and rejects failed/skipped/flaky/empty results. Browser tooling is installed at exact locked Playwright Test 1.65.1. The first diagnostic browser run passed; clean-revision verification remains pending. Browser reports remain separate from npm verification and manual acceptance. The original technical cases live in editor-regression-spec, while editor-acceptance is a smaller owner UX review.

## Collection interaction and recoverable deletion
Collection toolbar is shared; optional sort direction on version-1 saved views/history keeps older definitions valid and preserves high-first Priority defaults. Sort uses field direction plus stable title/ID tie breaks, and search matches all whitespace-separated terms. Direct edit uses the canonical record route and transient editor intent, not a second mutation implementation. Contextual creation opens editing after server acknowledgement. Reader focus resolves only inside visible records; saved-view completion cannot navigate after its initiating history entry has changed. Trash moves original Markdown into a sibling trash/<record-id>/<record-id>.md directory, preserving bytes and identity. Expected revisions and process-local serialization guard changes; exclusive directory creation protects previous trash, exclusive hard-link restoration protects canonical files. No permanent-delete endpoint. A filesystem that does not support hard links rejects restoration without discarding the trash entry. External edits are not transactionally locked; inspect any reported conflict or partial cleanup. Trash is Git-trackable project data. Relationships and review runs are retained; a removed record may produce missing-link findings until restored. Browser-local recovery is checked before move, not a distributed lock or deletion of recovery data. Changes to actual project records affect the working tree, so tests use isolated fixtures.

Collection polish: each sortable header reserves an identical indicator slot. New records store optional ISO createdAt and updatedAt in Markdown metadata; actual successful content edits set updatedAt, no-op saves and trash/restore preserve metadata. Legacy missing dates remain unknown, external file changes do not invent or refresh authored dates, and unknown dates sort last in either direction. Date sorts default newest first. A native modal dialog with focus restoration, Escape cancellation, current incoming links, recovery guard and pending/error states replaces browser alert/confirm for moving records to Trash. Original revision and recovery are rechecked before mutation; backend checks remain authoritative.

## Record commands and relationship selection
Shared RecordActions uses a native auto popover in the top layer, positioned against its trigger and viewport, with menu keyboard navigation and focus restoration. No nested link/button and no bubbling action clicks into row navigation. Edit uses the canonical editor; direct collection trash uses the same dialog and backend as detail trash, checks current record revision and recovery state, retains collection context and reports success only after acknowledgement. Relationship selection filters compatible, non-self and nonduplicate targets by tokenized title/ID/type/tag search, shows count and bounds the displayed options to 50; refine the query to reach further matches. No new data schema or dependency.

## Record management increment
Status and Priority use a strict revision-checked partial mutation; no unrelated fields accepted. Table inline edit and bounded (100 visible records) bulk edit call the same endpoint, check browser-local recovery before each operation, and acknowledge each result independently. Selection clears on route/view/filter changes; external disappearance prunes selected IDs. Bulk writes are sequential, not transactional, and uncertainty is reported rather than retried. Duplicate copies saved editable content into a new Concept record and fresh timestamps; scope links, reserved workflow tags, unknown metadata and implementation/acceptance evidence are deliberately not inherited. Stable record link copying has a visible fallback.
Increment is a normal canonical record. The Contains relationship explicitly scopes Milestone→Increment→Task/Test; generic links do not imply membership. Scope is derived, not duplicated as another task list. Overview and milestone surfaces navigate to increment detail. Detail renders authored readiness, linked commits, project-wide npm and browser verification with exact HEAD comparison, and latest matching definition/revision acceptance run per test. Invalid or unreadable scope/evidence is visible. Newer review decisions supersede older matching decisions. Browser evidence uses a strict bounded reader of .prism/cache/browser/latest.json, rechecks counts, cleanliness and exit codes; report paths are not used for arbitrary file access. Standalone projects retain scope even without Git. No automatic completion, GitHub live status, or integration authorization. PR references are authored Markdown context until a structured adapter is implemented.

## Hosted evidence boundary
A repository-mode registry entry may explicitly specify githubRepository (owner/repo). Only a deliberate Quality lookup sends an anonymous bounded request to api.github.com for ten recent workflow runs. No arbitrary host or redirect, credentials, private content, source files, artifact execution, GitHub mutation or automatic remote polling. Local service accepts only an empty JSON action and resolves the repository through its configured project ID; it does not take a repository or URL from the browser. Read result is a bounded in-memory observation (30-second refresh cache), not canonical data. Provider-reported head may differ from a PR's actual synthetic checkout; provider metadata is not attested artifact evidence or a manual acceptance decision. Explicit PR scope and job evidence remain later work.

## Versioned project property definitions
Optional schema.yaml under the data root defines version 1 fields by stable lowercase ID, kind, label and optional built-in type scope. Optional record customProperties stores primitive values keyed by field ID. Definitions use a constrained Zod contract, not executable expressions. Missing file means zero fields. Invalid definitions and removed/inactive fields never rewrite records; structural errors surface through record loading and semantic mismatches are visible in reading/editing. Only changed values are validated against the current schema, including same-project reference resolution. Custom writes require both record and exact schema-byte revision, with a final recheck; non-cooperating external filesystem writers still cannot be transactionally locked. Old clients omit customProperties and preserve stored values. Existing recovery drafts remain compatible; property map conflicts are explicitly reviewed as one field. Custom record types, schema administration, required-field migration, formulas and view-specific property columns are later increments. No new dependencies.

Schema administration uses the same project RecordStore serialization queue as record writes. Versioned definitions are checked against exact prior bytes, validated for non-destructive transitions, published atomically with an exclusive create for absent schema, then read back. Existing field identity/kind/scope and enum option identities are immutable via commands. Retirement is reversible and does not remove stored values. External processes are not transactionally locked. The UI protects open schema forms during navigation but does not yet recover them after reload.

Custom entity types extend rather than replace built-in semantic roles. The optional project entityTypes definition maps stable IDs to immutable roles; optional record customTypeId records classification, null is explicit unassignment, omitted changes preserve older values. Scoped property definitions may reference known compatible entity IDs. Definitions cannot remove or change existing roles via UI; retirement preserves identity and values while rejecting new assignment. Record assignment uses the same schema/record revisions and recovery model. Collection filters persist stable entity IDs; legacy saved views remain valid. Direct custom-type creation uses the same schema revision boundary. Type-specific view configuration and general schema migration remain separate follow-ups.


## M1 candidate architecture reconciliation

The preceding sections describe historical vertical slices. The M1 candidate adds configurable table presentation and stable saved date mappings; read-only planning, traceability and authored timeline projections; bounded search over saved canonical records and allowed source files; independent template instantiation; canonical inbox membership; native board movement through existing property commands; bounded unsaved command history and explicit opt-in autosave; project-scoped record and definition recovery. No automatic data conversion or inferred schedule. Local registration shares startup registry precedence and preflights disjoint data stores; offline backup/restore verifies exact bytes and refuses interrupted copies or existing destinations. In-app PR references use a separate revision-bound Increment command and never trigger a remote lookup. All remain subject to the consolidated M1 acceptance definition; see the authoritative roadmap records for boundaries and current evidence.

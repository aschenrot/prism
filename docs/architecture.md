# Architecture

## Decisions

- React + TypeScript + Vite for the interactive client; Fastify for a loopback-only local service.
- Markdown body + YAML frontmatter, one record per file. The API exposes parsed records with a SHA-256 revision derived from exact file bytes.
- Zod validates the initial entity contract. Future user-defined schemas should use JSON Schema and Ajv, with explicit migrations.
- TanStack Query owns server state. React component state owns temporary UI choices. A single command API owns mutations.
- Motion provides presentation transitions. HTML/CSS and SVG are the baseline rendering technologies.
- No mandatory database. A future SQLite/FTS5 index is derived and rebuildable, never authoritative.
- Git is version control, not real-time collaboration. The data folder may be a separate repository.
- Avoid desktop packaging, plugin runtimes, canvas engines and 3D libraries until their respective vertical slices are implemented.

## Data flow

File -> parse -> validate -> query -> projection (board/table/gallery/slides).
Inspector -> validated command + expected revision -> atomic write -> query invalidation -> all projections.

The current client polls the local API. A future file watcher plus server events can reduce polling. A stale revision returns HTTP 409. Invalid external files produce visible errors instead of being silently discarded. Atomic replacement prevents partial writes but cannot guarantee transaction isolation against non-cooperating external processes; the server serializes its own writes. Multi-record transactions and recovery journals are later work.

## Project format

`records/<id>.md`: YAML frontmatter with id, type, title, status, priority, tags, accent and relationships, followed by a Markdown body. Stable identifiers are generated by the server. Optional image/media support is later work; persisted view definitions are implemented as described below.

## Security boundary

Single local user. Server binds to loopback, validates Host and Origin, accepts JSON writes, and never executes record content. Record identifiers cannot contain path separators; symbolic-link record files are rejected. Remote access requires a separate authentication, authorization and deployment design. Do not expose this server through a reverse proxy.

## Multi-project boundary

The local registry is a YAML file containing explicitly configured absolute paths; the browser only sends validated project IDs. Each project has its own RecordStore, API URL namespace, and query cache namespace. Standalone projects keep records/; repository-mode projects use .prism/records/. A registry is machine-local; project records should remain Git-tracked. The browser cannot specify arbitrary root directories.

The initial repository reader is a bounded, read-only inventory of recognized source, documentation and manifest files in conventional directories. It rejects traversal and symlinks and never invokes compilers or project scripts. It is not a semantic parser or a sandbox for hostile local processes. Future adapters should emit normalized derived records with provenance (source, revision, timestamp, extraction method), kept separate from authored content. Runtime tools must be explicitly approved and disabled by default.

Audit findings are computed from canonical records, not stored as independent facts. Current checks cover missing descriptions and unresolved/self references; they do not imply implementation or verification coverage.

## Saved views and knowledge

View definitions are separate, versioned YAML files under the same project data root's views/ directory (repository mode: .prism/views/). They contain only configuration, not record copies. Each file has a stable ID and revision derived from bytes. Create/update/delete use a per-project serialized store, atomic replacement for writes, and optimistic conflict checks. Saved view queries use a shared pure selection function. Links and backlinks are computed from the canonical record list; they are not duplicated on disk. Relationships accept legacy string IDs (generic) and explicit {kind, target} objects. The shared relationship module derives labeled inverse edges and checks known endpoint constraints; Audit reports invalid endpoints and unresolved links. No inferred semantic migration or duplicate inverse storage. Wiki uses record bodies and the repository browser renders original Markdown, with raw HTML, external images and link navigation disabled. Neither is AI-generated documentation.

## Self-management workspace
The tracked .prism/projects.yaml is a portable registry with Prism's repository root as its first entry. Its records and saved views are real product knowledge, not frozen fixtures. A machine-local registry takes precedence. The read-only repository inventory supports src/, server/, shared/ and conventional documentation and test folders. Because Prism contains the examples, source browsing can include their tracked code, while their hidden data stores remain excluded and independently scoped. See docs/development-workflow.md for ownership and change conventions.

## Purpose-driven interface
The shared navigation module maps project profiles to purpose destinations with a default record filter and allowed view modes. This is a built-in configuration, not yet a user-editable navigation schema. Overview projections are derived directly from canonical records: active milestones, open tasks explicitly tagged blocker, task status counts and ordered milestone titles. Ready is an authored status, not proof of verification. Raw collections remain in Data library and saved view definitions remain independent. The same inspector supports expanded editing without remounting its draft state. No additional project data or dependencies are required.

## Git delivery evidence
Git is authoritative for commit history. The read-only adapter requires independent Git metadata and verifies the exact configured worktree root, captures HEAD, then reads at most 101 commits (100 displayed, one for truncation detection) with fixed argv, timeout and bounded output. It does not run scripts, change refs, request diffs or fetch remotes. Git must be installed and the repository trusted locally. A shallow or truncated history is explicitly partial. The optional implementationCommits metadata stores reviewed exact historical hashes, preserved by ordinary editor saves; new changes use Prism-Record trailers. Derived attribution never sets authored status or establishes CI acceptance. The browser cannot supply a Git command or arbitrary root.
